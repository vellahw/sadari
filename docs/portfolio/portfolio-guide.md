# 포트폴리오 활용 가이드

## 문서 목적

- 목적: Sadari 구현을 이력서, 포트폴리오 본문, 기술 면접과 시연에 활용할 수 있는 형태로 변환
- 적용 범위: 핵심 문장, 문제 해결 사례, 시연 순서, 예상 질문
- 기준일: 2026-08-11

## 포트폴리오 제목 예시

> 독서 기록을 소셜·알림·목표 관리로 확장하고 인증, 데이터 정합성, 운영 자동화까지 구현한 웹 서비스

## 프로젝트 소개 예시

Sadari는 카카오 도서 검색을 기반으로 독후감과 독서 목표를 관리하고, 공개 기록을 통한 팔로우·좋아요, 템플릿 알림과 PWA 푸시를 제공하는 독서 플랫폼이다. 사용자 서비스와 별도 관리자 서비스를 공유 MySQL 운영 테이블로 연결해 공통코드, 알림 템플릿, 사용자 메뉴, 스케줄러 실행 제어와 로그 조회를 구현했다. Spring Boot, MySQL 8.4, MyBatis, Redis와 React를 사용했으며, Kakao OAuth와 JWT 인증, SQL 조회 최적화, Aho-Corasick 비속어 탐지, CIELAB 표지 색상 매칭, Docker·GitHub Actions 배포 파이프라인을 구성했다.

## 이력서 핵심 문장

### 성능

- 마이페이지 독서 요약에서 주·월·연 단위로 반복되던 최대 19회의 SQL을 CTE 조건부 집계와 목록 1회 조회로 통합해 DB 왕복을 2회로 축소했다.
- 조회 목록을 현재 연도 범위로 제한하고 Java에서 한 번 순회해 기간별 목록을 구성함으로써 SQL 왕복 감소와 메모리 범위를 함께 고려했다.

### 알고리즘

- DB 공통코드 기반 비속어·예외 사전을 10분 캐시하고 Aho-Corasick 자동자로 구성해 입력 문자열을 사전 단어별로 반복 탐색하지 않도록 개선했다.
- 특수문자·숫자 우회 표현과 정상 예외 단어의 문자 범위를 함께 비교해 탐지율과 오탐 방지를 동시에 설계했다.
- 도서 표지의 대표 RGB를 표본 추출한 뒤 CIELAB 거리로 공통 팔레트와 매칭해 달력 색상을 자동 추천했다.

### 인증·보안

- Kakao OAuth 이후 Access/Refresh JWT에 기기별 `sid`를 포함해 HttpOnly Cookie로 발급하고, Redis의 기기별 Refresh Token 세션과 회원별 세션 색인을 Lua로 원자 생성했다. 닉네임은 세션 TTL 캐시로, 회원 상태는 로그아웃과 분리된 무기한 캐시로 관리했다.
- 현재·전체 디바이스 로그아웃, Access Token 블랙리스트, 다중 탭 Refresh Token 원자 회전과 BroadcastChannel 인증 동기화를 적용해 한 기기 로그아웃이 다른 기기 세션을 끊거나 동시 재발급이 세션을 파괴하지 않게 했다.
- 이미지 업로드에서 확장자가 아닌 파일 시그니처, 디코더 형식, 해상도, 픽셀 수를 검증하고 재인코딩해 위장 파일 저장을 차단했다.

### 데이터와 트랜잭션

- 외부 도서 검색 결과가 내부 DB에 없으면 ISBN 기준 도서 마스터를 생성한 뒤 독후감을 저장하는 흐름을 하나의 트랜잭션으로 구성했다.
- 신규 회원 닉네임을 공통코드 조합과 연월별 4자리 순번으로 발급하고 최초 동시 등록 충돌을 Unique Key 예외 후 재시도로 처리했다.

### 알림·운영

- 알림 문장을 템플릿과 `#{key}` 치환 Map으로 공통화하고 동일 알림의 1시간 중복 방지와 DB 커밋 후 FCM 발송을 적용했다.
- 별도 관리자 서비스에서 알림 템플릿과 사용자 메뉴를 관리하고 사용자 서비스가 공유 테이블에서 이를 소비하도록 제어면과 실행면을 분리했다.
- 관리자가 공통코드로 스케줄러 실행 여부를 제어하고 사용자 백엔드가 기록한 실행 마스터·실패 상세 로그를 관리자 화면에서 조회하도록 운영 피드백을 연결했다.

### 관리자 권한

- Redis 기반 관리자 세션과 메뉴별 조회·쓰기·삭제 권한을 적용해 공통코드, 알림 템플릿과 스케줄러 로그 같은 운영 기능의 접근 범위를 권한 그룹별로 통제했다.

### 배포

- Node·JDK·JRE 멀티 스테이지 Docker 빌드와 GitHub Actions를 구성해 통합 빌드, GHCR 이미지 발행, EC2 Docker Compose 배포와 상태 확인을 자동화했다.

## 대표 문제 해결 사례

### 사례 1. 마이페이지 조회 지연

**상황**

기간별 독서량과 목표를 조건만 바꿔 반복 조회하면서 한 화면에 최대 19회의 SQL이 실행됐다.

**행동**

CTE로 완료 독후감과 목표 기준 데이터를 한 번 구성하고 `SUM(CASE WHEN ...)` 조건부 집계로 기간별 값을 계산했다. 현재 읽는 책과 연간 완료 목록도 한 번 조회한 뒤 Java에서 분류했다.

**결과**

SQL 왕복을 19회에서 2회로 줄였다. 실제 응답 시간은 아직 운영 환경에서 측정하지 않았다는 한계도 함께 기록했다.

**근거**

- `docs/performance/my-page-reading-summary-optimization.md`

### 사례 2. 비속어 탐지 성능과 오탐

**상황**

사전 단어별 반복 검색은 사전이 커질수록 비용이 늘고, 문자 제거를 과도하게 적용하면 `보이지` 같은 정상 표현이 차단됐다.

**행동**

Aho-Corasick 자동자를 적용하고 차단·예외 사전을 같은 캐시로 관리했다. 숫자·특수문자 우회와 일반 문자열을 별도로 정규화하고 예외 단어가 차단 범위를 포함하는지 위치 기반으로 판단했다.

**결과**

한 입력에서 여러 사전 단어를 동시에 탐지하면서 숫자·특수문자 우회는 차단하고 일반 문자 삽입 오탐은 줄이는 정책을 구현했다.

**근거**

- `src/main/java/org/our/sadari/global/common/service/BadWordDetectionService.java`

### 사례 3. 알림과 DB 정합성

**상황**

트랜잭션 커밋 전에 푸시가 발송되면 사용자가 링크를 눌렀을 때 데이터가 아직 없거나 최종적으로 롤백된 화면에 접근할 수 있었다.

**행동**

알림 DB 저장은 업무 트랜잭션에 포함하고 FCM 발송은 `afterCommit` 콜백으로 분리했다. FCM 실패는 저장된 알림을 롤백하지 않고 경고 로그로 격리했다.

**결과**

알림센터 데이터의 정합성을 우선하면서 외부 메시징 장애가 핵심 업무를 실패시키지 않는 구조를 만들었다.

**근거**

- `src/main/java/org/our/sadari/alim/service/AlimServiceImpl.java`

### 사례 4. 인증 만료 무한 루프

**상황**

Access Token 만료 시 여러 API가 동시에 Refresh를 요청하거나 Refresh 요청 자체가 인터셉터에 걸리면서 로그인 화면과 본 화면이 반복됐다.

**행동**

한 탭에서는 재발급 Promise를 하나로 공유하고 요청별 재시도 상태를 기록했다. 서로 다른 탭과 서비스워커의 요청은 Redis Lua 스크립트로 기기별 Refresh Token을 원자 회전하고 10초 유예시간 동안 같은 최신 Token을 반환하게 했다. Refresh와 Logout 경로를 재발급 대상에서 제외하고 인증 Hook도 한 번만 복구를 시도하게 했다.

**결과**

한 탭의 동시 API 실패는 단일 Refresh 요청으로 수렴시키고 탭 사이의 재발급 경쟁은 같은 서버 회전 결과로 통합했다. 재발급 실패나 로그아웃은 BroadcastChannel 인증 이벤트로 같은 브라우저의 탭에 전파해 로그인 상태를 명확히 종료했다.

**근거**

- `src/main/frontend/src/app/api/axios.ts`
- `src/main/frontend/src/features/Auth/hooks/useCheckAuth.tsx`
- `src/main/java/org/our/sadari/global/security/jwt/TokenRedisService.java`
- `src/main/frontend/src/features/Auth/lib/authEvents.ts`

### 사례 5. 사용자 기능과 관리자 운영의 단절

**상황**

알림 문구, 사용자 메뉴와 스케줄러 실행 여부가 사용자 코드에 고정되면 작은 운영 변경에도 재배포가 필요하고, 배치 실패를 DB에서 직접 확인해야 했다.

**행동**

공통코드, 알림 템플릿과 사용자 메뉴를 공유 운영 테이블로 분리하고 `sadari-admin`에 관리 화면을 구현했다. 사용자 백엔드는 해당 설정을 실행 시점에 소비하고 스케줄러 결과를 마스터·실패 로그로 기록하게 했다. 관리자 서비스는 별도 Redis 세션과 메뉴별 권한으로 변경 주체를 제한했다.

**결과**

운영자는 코드 배포 없이 문구·메뉴·스케줄러 활성 상태를 조정하고, 사용자 백엔드가 남긴 실행 건수와 실패 원인을 관리자 화면에서 확인할 수 있다.

**근거**

- `docs/portfolio/admin-user-integration.md`
- `../sadari-admin/src/main/java/org/sadari/admin/sadariadmin/config/MenuPermissionInterceptor.java`

## 시연 순서

1. Kakao 로그인 후 자동 발급된 서비스 닉네임을 확인한다.
2. 카카오 도서 검색에서 책을 선택하고 표지 기반 자동 달력 색상을 확인한다.
3. 독후감을 등록하고 상세 화면에서 상태·평점·기간·기록을 직접 수정한다.
4. 마이페이지에서 현재 독서와 주·월·연 목표 요약을 확인한다.
5. 다른 사용자 프로필에서 팔로우 상태와 좋아요를 변경한다.
6. 알림센터와 읽지 않은 수, 푸시 설정을 확인한다.
7. 관리자 서비스에서 알림 템플릿 문구 또는 사용자 메뉴명을 변경하고 사용자 서비스 반영 흐름을 설명한다.
8. 관리자 권한 그룹별 메뉴 권한과 API 인터셉터 검증을 보여준다.
9. 공통코드로 스케줄러를 중지하고 사용자 백엔드가 남긴 실행·실패 로그를 관리자 화면에서 조회한다.
10. Swagger 접근이 ADMIN으로 제한되는 것을 설명한다.
11. GitHub Actions와 Docker Compose 배포 구성을 보여준다.

## 예상 면접 질문

### 왜 JPA 대신 MyBatis를 사용했는가

기간 집계, CTE, MySQL 저장 함수처럼 SQL 제어가 중요한 요구가 많아 쿼리를 명시적으로 관리하기 위해 MyBatis를 사용했다. 대신 Mapper XML 복잡도가 증가하므로 SQL 규칙과 문서, DTO를 통해 계약을 명확히 했다.

### 19회 SQL을 하나로 합치지 않고 왜 2회로 남겼는가

집계 결과는 단일 행이고 도서 목록은 다중 행이라 반환 구조와 용도가 다르다. 하나의 거대한 결과로 합치면 집계값이 목록 행마다 중복되고 매핑이 복잡해진다. 집계 1회와 제한된 목록 1회가 유지보수와 데이터 전송 측면에서 균형이 좋다고 판단했다.

### Redis가 없으면 로그인할 수 없는가

기기별 Refresh Token 세션, Access Token 블랙리스트, 회원 상태와 닉네임 캐시가 Redis에 있으므로 인증 수명주기의 핵심 의존성이다. Redis에서 `sid` 세션을 확인할 수 없으면 서명과 만료가 정상인 JWT도 인증하지 않는다. Redis 장애 정책과 고가용성 구성은 운영 배포 단계에서 추가해야 한다.

### FCM 발송이 실패하면 알림도 실패해야 하는가

아니다. 알림센터 데이터 저장을 기준 업무로 보고 FCM을 보조 채널로 분리했다. DB 커밋 후 FCM을 보내며 실패 시 저장 데이터는 유지한다. 재시도가 필요하면 Outbox 또는 메시지 큐로 확장할 수 있다.

### 비속어 캐시가 10분이면 변경이 늦게 반영되지 않는가

최대 10분의 반영 지연을 허용하는 대신 모든 사용자 입력에서 DB를 조회하지 않는다. 즉시 반영이 필요하면 관리자 변경 시 캐시 무효화 이벤트를 추가할 수 있다.

### Docker를 사용한 이유는 무엇인가

Node와 Java 빌드 환경, Redis, Firebase 인증 파일 경로와 운영 환경변수 주입 방식을 표준화하기 위해 사용했다. 멀티 스테이지 빌드로 실행 이미지에는 JRE와 WAR만 남겼다.

### 관리자와 사용자 서비스를 왜 API로 직접 연결하지 않았는가

공통코드, 템플릿, 메뉴는 사용자 요청마다 관리자 서비스의 가용성에 의존할 필요가 없는 운영 데이터다. 두 서비스가 같은 MySQL 데이터베이스의 테이블을 각자의 책임에 따라 작성·소비하도록 해 사용자 요청 경로에서 관리자 서비스 장애를 분리했다. 대신 스키마 계약과 캐시 전파 시점을 명확히 관리해야 한다.

### 관리자에서 바꾼 값은 즉시 반영되는가

설정마다 다르다. 알림 템플릿은 다음 알림 발송, 사용자 메뉴는 다음 경로 이동, 스케줄러 코드는 다음 Cron 실행에서 반영된다. 사용자 프론트 공통코드와 비속어 사전은 10분 캐시가 있어 최대 10분 지연될 수 있다.

## 과장하지 않아야 할 내용

- SQL 왕복 89.5% 감소를 실제 응답 시간 89.5% 개선으로 표현하지 않는다.
- 테스트 파일이 있다는 이유로 CI에서 테스트를 수행한다고 표현하지 않는다.
- EC2 배포 설정이 있다는 이유로 운영 서비스가 배포 완료됐다고 표현하지 않는다.
- 현재 구현되지 않은 AWS S3를 사용 기술에 포함하지 않는다.
- FCM 발송 실패 재시도와 다중 서버 스케줄러 분산 잠금이 구현됐다고 표현하지 않는다.
- `sadari-admin`도 사용자 서비스와 동일한 Docker·GitHub Actions로 배포된다고 표현하지 않는다.
- 관리자 화면에 스케줄러 수동 실행·재처리 기능이 있다고 표현하지 않는다.
